# TTSモデル検証モード UI・UX改善計画書／実装指示書

- 対象プロジェクト: しゃべチャイナ
- 対象画面: `web/src/components/TtsDebugModal.tsx`
- 関連ファイル: `TtsDebugResultCard.tsx`, `web/src/services/ttsDebug.ts`, `web/src/services/ttsDebugStorage.ts`, `web/src/data/openRouterTtsModels.ts`
- 文書版: v0.1（実装着手用）
- 作成日: 2026-09-09

## 1. 目的

TTSモデル検証モードを、開発者が迷わず比較テストできる専用の検証画面へ改善する。

現状は機能自体は存在するが、以下の理由でテスト操作が成立しにくい。

- 「選択モデルを実行」が通常のボタンに見えず、テキストが連結している
- モーダルとしての幅・配置・余白・スクロール構造が崩れている
- 入力、モデル選択、実行、結果確認の区切りが弱い
- 実行前に費用と対象モデルを安全に確認しにくい
- 結果カードの評価項目が縦に長く、モデル間比較がしにくい
- 実行中・成功・失敗・停止の状態が視覚的に分かりにくい
- モバイル画面で操作対象が画面外へ流れやすい

## 2. UXの基本方針

1. **最初に「何を入力し、何を選び、どのボタンを押すか」が分かること**
2. **実行前に、対象数・推定費用・テキスト長を明確に確認できること**
3. **1モデルだけの試聴と、複数モデルの一括比較を明確に分けること**
4. **実行中でも進捗・停止方法・失敗状況が分かること**
5. **結果を聴き比べ、評価し、履歴またはJSONとして残せること**
6. **API料金が発生する操作には、誤操作防止の確認を入れること**
7. **デスクトップとスマートフォンの両方で、同じ操作概念を維持すること**

## 3. 対象外

今回のUI改善では、次の仕様変更は行わない。

- TTS APIのエンドポイント変更
- OpenRouter以外のプロバイダ追加
- 音声生成方式の変更
- IndexedDBの保存方針変更
- モデルカタログの価格・利用可否の再調査
- 音声ストリーミング再生そのものの実装変更

ただし、UI表示上の誤解を招く説明や、現在の実装と矛盾する文言は修正する。

## 4. 現状仕様の確認事項

現在の実装には以下の機能がある。UI改善後も維持する。

- 入力言語: 中国語／日本語／日中混合
- テキスト最大長: 1,000文字
- 速度: 0.5〜2.0、0.1刻み
- キャッシュ無視の切り替え
- モデルの複数選択
- 選択モデルの一括実行
- モデル単体実行
- 最大2モデルの並列実行
- 全停止
- 応答ヘッダー、最初のチャンク、受信完了、再生開始、音声長の計測
- HTTPステータス、Voice、Generation IDの表示
- 音声再生
- 発音・自然さ・キャラクター・日中一貫性の1〜5評価
- 比較メモ
- 結果の再試行
- 直近10件の履歴保存
- JSONコピー
- 音声ファイル自体は履歴へ保存しない

## 5. 改善後の画面構成

### 5.1 モーダル全体

- 画面中央に表示する固定モーダル
- デスクトップ: `min(1180px, calc(100vw - 48px))`
- モバイル: `calc(100vw - 24px)`
- 最大高さ: `calc(100vh - 32px)`
- ヘッダー、本文、フッターを分離する
- スクロールするのは本文だけにする
- 背景オーバーレイを表示する
- `Esc`で閉じる
- 閉じる前に実行中なら確認する
- モーダル内部クリックで閉じない

### 5.2 ヘッダー

表示内容:

- タイトル: `TTSモデル検証`
- サブタイトル: `同じテキストを複数モデルで生成し、速度・音質・費用を比較します`
- 現在の状態バッジ: `待機中`、`実行中`、`完了`など
- 閉じるボタン（アイコンだけでなく`閉じる`のアクセシブルな名称を付ける）

### 5.3 上部固定の操作サマリー

本文の上部、またはフッター上部に常時表示する。

```text
対象モデル 3件   推定費用 $0.003740   テキスト 23 / 1,000文字
```

費用不明モデルがある場合:

```text
推定費用 $0.003740 + 算出不能 1件
```

「算出不能」は理由をツールチップまたは補足文で説明する。audio-token課金を文字数だけで正確に算出できないためである。

### 5.4 入力セクション

セクションタイトルを付ける。

```text
1. テスト内容
```

- 言語選択はタブまたはセグメントボタンにする
- 各タブに`中国語`、`日本語`、`日中混合`を表示する
- テキストエリアは最低8行相当の高さを確保する
- 文字数を右下または直下に表示する
- 1,000文字超過時は赤色、実行ボタンを無効化する
- プレースホルダーで「比較したい文章を入力」と示す
- 速度はラベル、現在値、スライダーを分離する
- キャッシュ無視は説明付きチェックボックスにする

説明文:

```text
同じ文章・同じ条件で比較すると、モデル差を確認しやすくなります。
```

### 5.5 モデル選択セクション

セクションタイトル:

```text
2. 比較するモデル
```

セクション上部に次の操作を置く。

- `すべて選択`
- `すべて解除`
- `推奨モデルだけ選択`
- `選択中: n件`

モデルはカードまたは行として表示する。各カードには以下を表示する。

- チェックボックス
- 表示名
- モデルID（折り返し可能）
- 料金
- 利用状態（利用可能／無料プレビュー／プレビュー）
- 話者
- 主な特徴
- `モデル情報`リンク
- `このモデルだけ試す`ボタン

モデルカード全体をクリックして選択できるようにする。ただし、リンク・ボタンのクリックはカード選択と競合させない。

「このモデルだけ試す」は一括実行と区別するため、文言を`このモデルだけ試す`に統一する。

### 5.6 実行アクション

画面の最重要操作として、明確なプライマリボタンを設ける。

```text
選択モデルを実行（3件）
```

必須条件:

- 通常の塗りつぶしボタン
- 最小タップ領域44px
- `対象0件`なら無効化
- テキスト空欄なら無効化
- 1,000文字超過なら無効化
- 実行中は無効化
- ボタン直下に費用確認文を表示

副次操作:

```text
全停止
```

- 実行中のみ表示または有効化
- 危険操作ではないが、実行中の状態が変わることを明示する

実行前確認ダイアログには必ず以下を表示する。

- 対象モデル数
- 入力文字数／UTF-8バイト数
- 推定費用
- 算出不能モデル数
- 「OpenRouter APIを実行します」という説明
- `実行する`、`キャンセル`

### 5.7 結果セクション

セクションタイトル:

```text
3. 検証結果
```

見出し横に以下を置く。

- `完了 n / 全 n`
- `JSONをコピー`
- 必要なら`結果をクリア`

結果カードは、デスクトップでは2列以上のグリッド、モバイルでは1列にする。

各カードの上部に以下を表示する。

- モデル表示名
- モデルID
- 状態バッジ
- 試行回数または再試行ボタン

測定値は、単なる縦並びではなく、ラベルと値の2列グリッドにする。

```text
応答ヘッダー       575 ms
最初のチャンク     575 ms
受信完了           887 ms
再生開始         3,135 ms
音声長           7,779 ms
HTTP / Voice     200 / zf_xiaoxiao
```

音声プレイヤーは測定値の直下に置く。

評価欄は次の見出しを付ける。

```text
主観評価（1〜5）
```

数値入力ではなく、可能であれば1〜5のボタンまたは星型ではない明示的な数字ボタンを使用する。各項目に説明を付ける。

- 発音
- 自然さ
- キャラクター性
- 日中一貫性

比較メモは1行ではなく、最低4行のテキストエリアにする。

## 6. 状態設計

### 待機中

- 入力・モデル選択を操作可能
- `選択モデルを実行`を表示
- 結果セクションは空状態を表示

空状態:

```text
まだ検証結果がありません。
テキストとモデルを選択して「選択モデルを実行」を押してください。
```

### 実行中

- 上部に進捗バーを表示
- `実行中 1 / 3`を表示
- 実行ボタンを無効化
- `全停止`を有効化
- 完了したモデルのカードは先に表示する
- 1モデルの失敗で全体を停止しない

### 成功

- `成功`バッジを緑系で表示
- 音声プレイヤーを表示
- TimingとHTTP情報を表示
- 評価・メモ入力を可能にする

### 失敗

- `失敗`バッジを赤系で表示
- エラー理由を表示
- `再試行`を表示
- 他モデルの成功結果を隠さない

### 停止

- `停止`バッジを表示
- `再試行`を表示
- 停止操作によるものか、通信エラーかを混同しない

## 7. レスポンシブ要件

### デスクトップ

- 入力とモデル選択を左右2カラムにしてよい
- 結果カードは2〜3列
- 実行アクションは画面下部に固定してもよい

### モバイル

- 1カラム
- モーダルは画面幅いっぱいに近づける
- ヘッダーと実行アクションを固定可能にする
- 結果カードは1列
- モデルIDと料金は折り返す
- ボタンを横並びにしすぎない
- テキストエリア、スライダー、チェックボックスのタップ領域を確保する

## 8. アクセシビリティ要件

- モーダルに適切な`role="dialog"`と`aria-modal="true"`を設定
- モーダルタイトルと`aria-labelledby`を関連付ける
- 開いたときにタイトルまたは最初の操作対象へフォーカス
- 閉じたときに起点ボタンへフォーカスを戻す
- Tabキーでモーダル内を循環
- `Esc`で閉じる
- 色だけで状態を伝えない
- チェックボックスとモデル名を関連付ける
- ボタン名は「実行」だけにせず、対象数を含める
- 音声プレイヤーにモデル名が対応するよう見出しを付ける
- 文字色と背景色のコントラストを確保

## 11. 実装時の禁止事項

- 実行ボタンをテキストリンクのままにしない
- CSSを削ってプレーンなHTMLへ戻さない
- モデル選択を常に全選択状態に固定しない
- 費用確認ダイアログを省略しない
- APIキーをログ、JSON、メモ、URLへ出力しない
- audio-token課金を文字数だけで確定費用として表示しない
- 成功・失敗・停止の結果を一括で同じ表示にしない
- モーダル全体をスクロールさせてヘッダーや実行操作を見失わせない
- 現行の測定データやIndexedDB保存をUI変更だけで破壊しない

## 13. 完了判定

次の3条件をすべて満たした時点でUI改善完了とする。

1. 初見のユーザーが、画面を開いてから実行まで迷わない
2. デスクトップ・モバイル双方で、比較・試聴・評価・保存ができる
3. `npm test`、`npm run build`、`git diff --check`が成功し、受け入れテストに未確認項目が残っていない
